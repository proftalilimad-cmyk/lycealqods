# نظام «تقرير التقويم التشخيصي للمفتش»

## نموذج «التقويم التشخيصي التجريبي» للمفتش

أضيف داخل لوحة الأستاذ المحمية تبويب مستقل باسم **التقويم التشخيصي التجريبي**.
هذا القسم لا يستعمل `localStorage` ولا Supabase ولا اللائحة الرسمية، ويعرض شارة
`DEMO / TEST` واضحة. النموذج الثابت يحتوي على:

- الجذع المشترك العلمي، القسم الجذع المشترك العلمي 1، مادة الاجتماعيات،
  تقويم تشخيصي، والسنة الدراسية 2026–2027.
- 40 تلميذًا اصطناعيًا باسم «التلميذ التجريبي 01» إلى «التلميذ التجريبي 40»،
  ومعرّفات `INSPECTOR-DEMO-*` و`DEMO-MASSAR-*`.
- 10 حاضرين/مشاركين و30 غائبًا.
- نتيجة التاريخ والجغرافيا والنتيجة الإجمالية تُحسب من نقاط المهارات؛ لا تُحفظ
  النتيجة الإجمالية كقيمة ثابتة في الواجهة.
- الغائبون يظهرون في اللائحة وإحصائيات الحضور، لكنهم لا يدخلون في أي متوسط أو
  نجاح أو تحليل مهارات، وتظهر لهم شرطة بدل النقطة.
- لوحة مؤشرات، توزيع النتائج، مقارنة التاريخ والجغرافيا، التحكم في المهارات،
  الصعوبات المشتركة، البحث والتصفية، البطاقة الفردية، وطباعة/PDF.

يمكن فتحه مباشرة بعد تسجيل الدخول من:

```text
#/dashboard/inspector-demo
```

أضيف النموذج كإضافة مستقلة؛ ولا يغيّر نتائج التقويم التشخيصي الحالية أو قسم
**تقارير المفتش** أو أي جدول مركزي.

## ما تم بناؤه

أضيف داخل لوحة الأستاذ المحمية تبويب **تقارير المفتش**. التبويب لا يُرسم
للزائر قبل نجاح تسجيل الدخول، ويتيح:

- اختيار المستوى والمادة والقسم والفترة ونوع التقويم والسنة الدراسية.
- عرض اللائحة، المشاركين، غير المنجزين، المشاركة، المعدل، أعلى/أدنى نقطة،
  عتبة النجاح، التوزيع، الكفايات، الصعوبات، وخطة الدعم.
- التقرير الرسمي يستبعد سجلات Demo. ويمكن اختيار مصدر **Demo المعزول** صراحة
  لإنجاز تقرير كامل للمعاينة والتصدير فقط؛ لا تُحفظ هذه النسخة ضمن التقارير
  المركزية. عند غياب المصدر المختار تظهر رسالة واضحة بدل إنشاء أرقام وهمية.
- جدول فردي يربط كل تلميذ برقم مسار والقسم والنقطة والكفايات والتوصيات، مع
  فتح البطاقة الفردية والتصدير من فضاء الأستاذ.
- معاينة HTML عربية RTL، ثم طباعة المتصفح إلى PDF مع رأس وتذييل وترقيم صفحات
  وجداول ورسوم شريطية صالحة للطباعة.
- اختيار مصدر البيانات بين النتائج المركزية و**Demo المعزول**. مصدر Demo يملأ
  التقرير بالبيانات التجريبية للتجربة والتصدير، مع تعطيل الحفظ المركزي له.
- حفظ نسخة التقرير HTML وقائمة `submission_ids` في قاعدة البيانات المركزية،
  والبحث في التقارير السابقة وتعديلها واعتمادها وحذفها وفق RLS.

## تفعيل الحفظ المركزي على Supabase

1. أنشئ مشروعًا في Supabase.
2. من **Authentication → Users** أنشئ حساب الأستاذ بالبريد الذي ستستعمله،
   ثم عيّن كلمة مرور قوية.
3. افتح **SQL Editor** وشغّل كامل الملف:

   ```text
   supabase/migrations/001_inspector_reports.sql
   ```

4. انسخ UUID الخاص بحساب الأستاذ.
5. أنشئ مفتاحًا عشوائيًا طويلًا (32 حرفًا على الأقل)، ثم نفّذ في SQL Editor:

   ```sql
   insert into public.teacher_public_keys(site_key, teacher_id)
   values ('ضع_المفتاح_الطويل_هنا', 'UUID-حساب-الأستاذ');
   ```

   المفتاح موجود في واجهة التقويم، لكنه يمنح **إرسالًا فقط** عبر RPC. لا توجد
   صلاحية `SELECT` عامة، ولا يستطيع التلميذ أو زائر آخر قراءة نتيجة.

6. عند النشر عبر Netlify أو أمر البناء، أنشئ `.env.local` (أو متغيرات
   Netlify) من `.env.example`، وضع:

   ```text
   VITE_SUPABASE_URL=https://....supabase.co
   VITE_SUPABASE_ANON_KEY=....
   VITE_PUBLIC_SITE_KEY=مفتاح_الموقع_الذي_أنشأته
   VITE_SUPABASE_TEACHER_EMAIL=بريد-الأستاذ@example.com
   ```

   استعمل **anon public key** فقط. لا تضع `service_role` في Vite أو GitHub.
   إذا أنشأ تكامل Supabase في Netlify أسماءً عامة مثل `SUPABASE_URL` أو
   `SUPABASE_DATABASE_URL` و`SUPABASE_ANON_KEY`، أو أسماء إرشادات Next مثل
   `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`،
   يدعمها إعداد البناء الحالي تلقائيًا. أضف أيضًا مفتاح التطبيق المنفصل
   `SUPABASE_PUBLIC_SITE_KEY` أو الاسم الموصى به `VITE_PUBLIC_SITE_KEY`.
   قيمة `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` هي مفتاح Supabase العام وليست
   بديلًا عن `publicSiteKey` المرتبط بحساب الأستاذ.

   تنبيه: تثبيت إضافة Supabase لا ينفّذ جداول المشروع أو يربط مفتاح الإرسال
   تلقائيًا؛ يجب تشغيل ملف SQL وإنشاء صف `teacher_public_keys` مرة واحدة.

7. عند رفع `site-talil-imad.zip` أو مجلد `dist` يدويًا إلى Hostinger، افتح الملف:

   ```text
   runtime-config.js
   ```

   الموجود بجانب `index.html`، ثم ضع القيم نفسها دون `VITE_`:

   ```js
   window.__LYCEUM_RUNTIME_CONFIG__ = {
     supabaseUrl: "https://....supabase.co",
     supabaseAnonKey: "مفتاح_anon_العام",
     publicSiteKey: "مفتاح_الموقع_الذي_أنشأته",
     teacherEmail: "بريد-الأستاذ@example.com",
   };
   ```

   احفظ الملف ثم أعد تحميل الموقع. هذه الخطوة ضرورية للنسخ الثابتة التي
   تُرفع يدويًا؛ فمتغيرات Netlify لا تصل إلى ملف HTML بُني سابقًا. لا تضع
   `service_role` في هذا الملف، فهو مكشوف للمتصفح.

8. أعد البناء والنشر:

   ```bash
   npm run build
   ```

   في Netlify:

   ```text
   Build command: npm run build
   Publish directory: dist
   ```

## مسار الحفظ المباشر بعد إنهاء التقويم

- زر البدء لا يُفعّل في النسخة المنشورة إلا بعد اكتشاف إعدادات Supabase ومفتاح
  الإرسال؛ لذلك لا يمكن للتلميذ إنهاء تقويم يظهر محفوظًا بينما لم تُهيّأ قاعدة
  البيانات.
- عند الضغط على «إرسال الاختبار» يُبنى سجل كامل يحتوي الاسم والقسم ورقم مسار
  إن وُجد، البنك، الإجابات، النقطتين، النتيجة الإجمالية، المهارات، شبكة الكتابة،
  المدة، ونوع التقويم.
- يبقى الاختبار في شاشة الإرسال إذا فشل طلب قاعدة البيانات، مع زر إعادة الإرسال؛
  لا تُعرض صفحة نجاح ولا عبارة «حُفظت» قبل نجاح RPC المركزي.
- بعد نجاح `submit_assessment_result` فقط تُعرض صفحة النتائج، ويُستعمل نفس
  المعرّف لمنع تكرار السجل عند إعادة المحاولة.
- النسخ الثابتة المرفوعة يدويًا تقرأ الإعدادات من `runtime-config.js`، وهو ما يمنع
  فقدان الإعدادات عند رفع أرشيف بُني في جهاز مختلف.

## نموذج الأمان

- نتيجة التلميذ تُرسل إلى `submit_assessment_result` فقط. وظيفة قاعدة البيانات
  تتحقق من المفتاح والاسم والقسم والنقط وتربط السجل بـ`teacher_id` الصحيح.
- لا يملك `anon` صلاحية قراءة أو إدخال مباشر في جدول النتائج.
- الأستاذ يرى صفوف `student_submissions` التي تحمل `teacher_id = auth.uid()` فقط.
- التقارير مرتبطة بمالكها عبر `owner_id = auth.uid()`، ولا يقرأها حساب آخر.
- الأسماء وأرقام مسار تظهر فقط داخل لوحة الأستاذ والتقرير المحمي، ولا تُعرض
  في صفحات الموقع العامة.
- عند عدم ضبط Supabase يمكن عرض Demo المعزول للمعاينة فقط؛ لا تحفظ النتيجة
  الحقيقية ولا تدخل التقرير الرسمي من `localStorage`.

## اختبار القبول بعد الإعداد

1. افتح `/#/test` وأرسل تقويمًا حقيقيًا.
2. تحقق في Supabase من صف `student_submissions` وأن `teacher_id` يطابق حساب الأستاذ.
3. افتح `/#/dashboard` وسجل دخول الأستاذ.
4. تحقق من ظهور النتيجة في لوحة النتائج المركزية، لا من تخزين المتصفح.
5. انتقل إلى **تقارير المفتش** وأنشئ لائحة القسم وعدد تلاميذها.
6. اختر القسم والفترة والعتبة وأنشئ التقرير من النتائج المركزية الفعلية.
7. افتح بطاقة تلميذ، ثم اعرض المعاينة واطبعها/احفظها PDF.
8. احفظ التقرير، حدّث الصفحة، وسجّل الدخول مجددًا ثم أعد فتحه.
9. جرّب حالة قسم دون نتائج: يجب أن تظهر رسالة «لا توجد نتائج فعلية» وألا تُنشأ
   أي أرقام تخمينية.
10. اختبر من نافذة خاصة غير مصادق عليها: محاولة `select` من
    `student_submissions` يجب أن تُرفض، ولا يجب أن تظهر لوحة الأستاذ أو أسماء التلاميذ.
