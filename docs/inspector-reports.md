# نظام «تقرير التقويم الشخصي للمفتش»

## ما تم بناؤه

أضيف داخل لوحة الأستاذ المحمية تبويب **تقارير المفتش**. التبويب لا يُرسم
للزائر قبل نجاح تسجيل الدخول، ويتيح:

- اختيار المستوى والمادة والقسم والفترة ونوع التقويم والسنة الدراسية.
- عرض اللائحة، المشاركين، غير المنجزين، المشاركة، المعدل، أعلى/أدنى نقطة،
  عتبة النجاح، التوزيع، الكفايات، الصعوبات، وخطة الدعم.
- استبعاد سجلات Demo من التقرير الرسمي؛ عند غياب النتائج تظهر شرطة/صفر مع
  تنبيه صريح بدل إنشاء أرقام وهمية.
- جدول فردي يربط كل تلميذ برقم مسار والقسم والنقطة والكفايات والتوصيات.
- معاينة HTML عربية RTL، ثم طباعة المتصفح إلى PDF مع رأس/تذييل وترقيم صفحات
  وجداول ورسوم شريطية صالحة للطباعة.
- حفظ نسخة التقرير HTML وقائمة `submission_ids` في قاعدة البيانات المركزية،
  والبحث في التقارير السابقة وتعديلها واعتمادها وحذفها وفق RLS.

## تفعيل الحفظ المركزي على Supabase

1. أنشئ مشروعًا في Supabase.
2. من **Authentication → Users** أنشئ حساب الأستاذ بالبريد الذي ستضعه في
   `VITE_SUPABASE_TEACHER_EMAIL`، ثم عيّن كلمة مرور قوية.
3. افتح **SQL Editor** والصق الملف:

   ```text
   supabase/migrations/001_inspector_reports.sql
   ```

4. أنشئ نسخة `.env.local` (أو متغيرات Netlify) من `.env.example`، وضع:

   ```text
   VITE_SUPABASE_URL=https://....supabase.co
   VITE_SUPABASE_ANON_KEY=....
   VITE_SUPABASE_TEACHER_EMAIL=بريد-الأستاذ@example.com
   ```

   استعمل **anon public key** فقط. لا تضع `service_role` في Vite أو GitHub.

5. أعد البناء والنشر:

   ```bash
   npm run build
   ```

   في Netlify:

   ```text
   Build command: npm run build
   Publish directory: dist
   ```

6. سجّل دخول الأستاذ بالبريد وكلمة المرور الخاصة بـSupabase. عندها تصبح
   شارة التبويب **قاعدة مركزية مفعّلة**، وتصبح النتائج التي يرسلها التلميذ
   قابلة للجلب في لوحة الأستاذ من أي جهاز.

## نموذج الأمان

- نتيجة التلميذ تُرسل إلى `student_submissions`، وتوجد سياسة INSERT فقط للدور
  العام؛ لا توجد سياسة قراءة للدور `anon`.
- لا يقرأ النتائج إلا مستخدم مصادق عليه، والتقرير لا يُحفظ إلا مع `owner_id`
  يساوي `auth.uid()`.
- سياسات SELECT/UPDATE/DELETE لتقارير المفتش مربوطة بمالك التقرير.
- الأسماء وأرقام مسار تظهر فقط داخل لوحة الأستاذ والتقرير المحمي، ولا تُعرض
  في صفحات الموقع العامة.
- عند عدم ضبط Supabase يمكن المعاينة والطباعة، لكن الواجهة تقول صراحة إن
  الحفظ الدائم غير مفعّل؛ لا تُعامل `localStorage` كقاعدة بيانات مركزية.

## ملاحظات تشغيلية

- التطبيق الحالي يرسل التقويمات المنجزة بنوع `diagnostic`. إذا اختير
  `personal` في التقرير، فلن تظهر نتائج تشخيصية ضمنه؛ هذا مقصود حتى لا تختلط
  أنواع التقويم.
- تُحسب النتائج من الحقول المحفوظة في `Submission` ومن بنك الأسئلة/شبكة
  التنقيط الموجودة في المشروع، ولا يُعاد احتساب أو اختراع نتيجة تلميذ غائب.
- نسخة PDF تُنتج بواسطة محرك طباعة المتصفح بعد المعاينة. النسخة HTML الكاملة
  تحفظ مركزيًا لتتمكن من إعادة فتح التقرير حتى قبل تنزيل PDF؛ حفظ ملف PDF
  ثنائي في Storage يمكن إضافته لاحقًا إذا فُعّلت سياسة Storage منفصلة.
- يجب اختبار RLS بحساب الأستاذ وبنافذة خاصة غير مصادق عليها: الزائر العام
  يجب أن يحصل على رفض عند محاولة `select` من الجدولين.
